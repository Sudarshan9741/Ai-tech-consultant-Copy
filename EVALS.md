# Evaluation Results

## Scope and method

The current checked-in test files contain 41 tests: 22 for Task 1 (including seven scheduler/retry regressions), 10 for Task 2, and 9 for Task 3. Each task includes a 20-case evaluation. `test_all.bat` now selects a temporary Task 1 database and random local integration port, disables scheduled sync, and passes that endpoint to Tasks 2 and 3. The evaluation results recorded below are prior local runs; timings are single-run wall-clock measurements, not latency distributions.

**Previously recorded suite results:** 38 tests passed across separate isolated task runs (20 + 9 + 9) using a temporary Task 1 API and database snapshot. That was an earlier test inventory, not one `test_all.bat` run, and does not cover the two later regression tests now present.

**Latest verified Task 2 checks (18 October 2026):** `npm run lint` passed (`tsc --noEmit`, exit 0). A filtered run of eight local unit tests passed (8 passed, 0 failed); it excluded the Task 1 HTTP integration test and the 20-email benchmark. No full-suite result is claimed from this check.

**Latest verified aggregate run (19 October 2026):** `test_all.bat` passed all 41 tests using a temporary Task 1 database, a random Task 1 integration port, and scheduled sync disabled: Task 1 22/22, Task 2 10/10, Task 3 9/9. This run did not contact the live sitemap, send email, or make a paid model request.

The test cases and expected labels are defined in each task's test file. Task 1 evaluates answered-versus-escalated outcomes. Task 2 evaluates intent labels and basic draft structure. Task 3 evaluates native-versus-custom platform checks through the actual Task 1-backed checker. These tests do not score prose quality with human raters.

## What each evaluation measures

**Task 1.** The 20 queries consist of 15 Brilliant Directories help questions and five unrelated questions. A case is correct when the API answers the in-domain question or declines and escalates the out-of-domain question as expected. Separate tests check that cited sources and image metadata are returned, unrelated evidence is pruned, and a verified escalation answer can be retrieved after it is indexed. The benchmark's 100% result is on this fixed, local set; it does not establish recall across the live help center.

**Task 2.** The dataset contains 61 sample emails. The 20-email set has expected intent labels recorded in the test (one procedural refund request, nine how-to questions, and ten billing cases). The benchmark checks each generated draft's category, minimum length, confidence bound, and inclusion of the recipient's name. The reported 100% is intent-label accuracy, with all 20 basic draft assertions passing. No human rating or semantic factuality review of the prose was performed. The measured latency includes sequential Task 1 calls and will vary with service load.

**Task 3.** Twelve of the 20 labeled feature requirements are expected to map to native settings; eight are expected to require custom work. The test runs them through the actual platform-checking agent and Task 1 API, then compares the result with the fixed labels. A correct result on this set does not show that the estimates match completed project outcomes. The case set and its labels are hand-authored.

## Interpretation

The task-specific test targets pass on the recorded sets. The tests are useful regression checks for the behaviors they exercise, not evidence that the system is production-ready. In particular, deterministic template quality, customer satisfaction, crawler freshness, estimate calibration, and human-review burden have not been measured in a field study.

The local timings are for the current machine and local processes. They are not comparable to the old live-Claude latency rows because no live Claude measurements were collected under the same inputs or conditions. The test suite has no token accounting, invoice data, repeated trials, confidence intervals, or blinded human graders. Therefore it cannot support a model ranking or cost-per-1,000 estimate.

Provider cost was not instrumented or measured. A controlled model comparison with fixed inputs, human-reviewed quality labels, repeated latency samples and recorded token usage remains an evaluation deliverable if required by the rubric.

## Limits and failure cases

- The 20-case sets are small and locally authored; they do not establish general performance on unseen customer data.
- Task 2's deterministic intent labels and basic body checks are not a human quality review of tone, correctness or customer satisfaction.
- Task 3's binary native/custom labels do not separately measure uncertainty calibration or estimate accuracy against completed projects.
- Task 1 schedules incremental sync on startup and at a configurable interval (daily by default), but live sitemap success is unverified; earlier connectivity failed. The current running Task 1 instance has scheduled sync disabled. Scheduler tests use mocked sync functions and do not establish live sitemap availability or production reliability.
- Task 2 review/audit history and approval streaks, and Task 3 SOW approvals, are process-local and are lost on restart.
- On this Windows machine, the Node.js 22.14.0 `os.userInfo()` check succeeds; no compatibility preload is required by the repository. `run.bat` checks health before starting services and disables scheduled Task 1 sync for safe demos.
- Real email transport is intentionally absent. Approval authorization does not prove safe delivery through a mail provider.
